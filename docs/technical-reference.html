Technical reference · current pilot build

System architecture

A single Python service on the Windows PC handles every call. Twilio reaches it through a Cloudflare tunnel. The service calls out to the AI model, Zoho Desk and local data files.

Inbound trust

Every /voice, /end and /relay request must carry a valid Twilio signature for the configured public URL and your Account SID. The relay also needs a one-time nonce issued in /voice.

State

Call state lives in memory: the session (nonce, end reason, ticket status) and the Conversation (history). Between calls, nothing is remembered. Only transcripts (when on) and the dry-run log are saved. A restart clears active calls.

Config

Read from private-config/twilio-pilot.json on every request, so model, effort, voice and ticket mode apply on the next call without a restart. Code changes need a restart.

Launcher

run.ps1 starts the tunnel, saves its URL, starts uvicorn and moves the number's webhook. It retries three times, then shows a READY or NOT READY banner.

Call lifecycle

From ring to hang-up

Three HTTP touchpoints frame each call. The conversation itself runs over one WebSocket, where Twilio sends finished caller sentences and the app streams reply text back.

Interruptions (barge-in)

Twilio sends {type: interrupt, utteranceUntilInterrupt}. The app cancels the running reply task, and the assistant turn in history is replaced with only the words the caller actually heard. The model never believes it said something the caller missed.

New caller sentence mid-reply

A new final prompt cancels any reply still in progress before starting the next one. Only one reply task runs per call at a time.

Failure handling

Any model, tool-limit or Twilio error sets reason error and ends the relay. The caller hears a fixed "encountered a problem" message, and the cause is logged in the pilot window (keys redacted). There are no automatic retries mid-call.

The AI conversation component

No pathway graph: one agent, rules, tools and code checks

Bland routes a call through a drawn graph of nodes and edges. Here there is one conversation loop. On every turn the model sees the same rules, the core knowledge and the whole call so far, and chooses the next step: speak, use a tool, or end the call. "Routing" is the model choosing a tool. The critical routes are backed by checks in code.

Inside one turn

What is sent to the model, and what comes back

Each caller turn rebuilds the request from the same parts. The fixed front part (rules + knowledge + tools) is cached by the API, so only the new conversation text is processed in full.

Memory model

Within a call: earlier turns are resent each turn, including their tool calls and results, so the agent doesn't repeat lookups. The harness found this was missing and it was fixed on 26 Nov. Between calls: nothing, by design. Continuity comes from Zoho tickets. Thinking blocks are never carried across turns, which keeps the history valid for the API's thinking checks.

Per-turn log line

[pilot] turn on …ab12cd: first word 820ms, total 2410ms, tools get_guide. Timings only. transcripts=on adds the full transcript (saved privately).

Staged knowledge · guarded ticket creation

Adding or changing a document

  • Edit or create the file in knowledge/content/ (through the document intake process)
  • Registry entry: bump version, set content_sha256, development_ready, export: true, a clear description (this is the guide-menu text)
  • New source? Add 'ID': 'core' | 'guide' | 'search' to DELIVERY in knowledge.py
  • Run the tests, then restart

  • configure.py --update-number: repoint the number if NOT READY
  • configure.py --set effort=medium: change a setting
  • zoho_desk.py --check: read-only Zoho sign-in test
  • transcripts.py --follow: watch calls live
  • harness.py · --only ID,… · --set thinking=…: conversation tests
  • -m unittest test_pilot test_claude test_stages test_harness: offline tests

Known pilot limitations

  • Quick-tunnel URL changes on every restart (fixed address planned)
  • Runs on one PC; in-memory state; 2 concurrent calls
  • No SMS, vouchers, payments or live transfer yet
  • Twilio's default speech recognition settings, apart from language and hints
  • Transcripts are on for the staff pilot: turn them off before any real patient data

Testing and observability

Conversation test harness

Runs the same engine as the phone in text, so behaviour changes can be checked in minutes for cents, before anyone calls. Speech and Twilio are not covered here; phone calls and live transcripts cover those.

Commands (voice-agent, .venv\Scripts\python.exe)

  • harness.py: all scenarios (≈ US$0.33) · --list · --only HW-01,TIX-01 · --tag safety
  • harness.py --repeat 3: run each scenario several times (AI replies vary)
  • harness.py --set thinking=between_tools: try a setting without changing the live pilot
  • transcripts.py --follow: watch real calls live (pilot, fictional details)

Found and fixed by the harness

  • Tool results were dropped between turns, so the agent re-ran lookups and guides every turn (slow, costly, odd apologies). Now kept in history.
  • Written formatting (bold, numbered lists) in spoken replies. A new spoken-style rule plus a check.
  • Judge misread approved steps as invented. The judge now sees the approved source text.

Open points

  • Sometimes asks two related questions in one reply (ID-01)
  • With thinking off, one formatting slip (**bold**) seen in 9 scenarios
  • Harness does not test speech recognition, voice or barge-in timing; phone checks still needed
